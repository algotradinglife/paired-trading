给用户列后续选项时，必须：
1. 给出**明确推荐**（不只是 1/2/3 罗列），即使是"先 X、然后 Y"这种顺序
2. 评估能否**并行推进**，能并行就并行（Workflow / 多 Agent 单消息），不要默认串行
3. **判断题就直接给意见，别甩选择题。** 当我已有足够上下文能下判断时，直接说"我建议 X，因为…"然后等一个 go-ahead，而不是把决策成本拆成 AskUserQuestion 菜单丢回给用户。

**Why:**
- 2026-06-08 原话："后续你给选项的时候，把推进的建议也给出来。而且尽可能采用并行推进的方案"。
- 2026-06-09 用户直接打断一个双问 AskUserQuestion："我想听你的意见，而不是我在做选择题"。同一 session 还有一次因为 AskUserQuestion 选项太抽象（一串 schema 字段名）看不懂，要求"结合上下文简单地阐述一下"。
- 结论：用户雇我是来做判断的，不是来出题的。多选题适合"真·偏好分叉"（无对错、看用户口味）；但凡是我能基于证据下结论的工程取舍，应该直接给带理由的推荐。

**How to apply:**
- 工程取舍（哪个方案、要不要做某优化、如何收尾）→ 先给**我的判断 + 理由**，结尾问一句"这样可以吗 / 要不要我就这么做"，而不是 2-4 个等权选项。
- 真正的偏好分叉（无客观最优）才用 AskUserQuestion。
- 用 AskUserQuestion / 提问时，先用**大白话 + 项目里的具体实例**把背景讲清楚，别堆字段名/术语；用户看不懂会直接喊停。
- 列 N 个候选 next step 时仍必须有"我建议"段（见上）。
- 独立小任务优先打包并行（Workflow / 并行 Agent 单消息）；互相依赖的（改代码 → 验证 → 落档）串行；并行前提是用户明确想推进，brainstorm 阶段先别并行。
